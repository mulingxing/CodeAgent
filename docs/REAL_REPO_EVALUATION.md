# 真实 Python 仓库试验记录

以下试验使用从“智能旅行助手”复制出的**独立、已提交的本地 Git 仓库**。原项目目录没有被修改；测试只在本地和无网络的验证容器中运行，外部地图与模型服务由测试桩替代。

| 问题 | 修复前 | CodeAgent 候选修复 | 独立复核 |
| --- | --- | --- | --- |
| POI 地图适配：成功结果被丢弃、上游异常被当成空结果 | 所选回归测试 3 项失败 | 修改地图服务与路由，所选验证通过 | 相关测试 36 项通过，42 个子测试通过 |
| 旅行日期：非法日期、倒序日期、天数与日期跨度不一致，计划末日缺少边界检查 | 所选日期测试 5 项失败、1 项通过 | 修改请求模型与行程校验，6 项通过 | 又补充日期格式边界，最终相关测试 41 项通过，42 个子测试通过 |

日期案例的前两条任务曾因 Agent 超时失败，未进入验证，也没有留下候选差异。排查发现需要修改约 19 KB 的源码文件，而当时 Agent 只有整文件重写工具。加入受限的局部片段替换工具后，同一问题在首次尝试中完成；这验证了修复工具设计对较大文件的影响。历史失败任务仍保留在页面，不代表最终回归失败。

地图候选改动还涉及天气、路线、地理编码与日志处理，范围超出了 POI 回归测试的直接覆盖。因此它保留在审核工作树中，不能仅凭上述测试通过就直接应用到真实旅行项目。日期最终候选由两轮修复组成，第二轮是在第一轮候选之上补充 `YYYY-MM-DD` 格式约束。

这两类试验支持的结论是：系统能在具备依赖、可运行回归检查的真实 Python 仓库副本上完成多文件修复，并展示失败、重试、验证和人工审核。它们尚不能证明任意领域的 Python 代码都能自动修复，也没有覆盖真实外部服务的端到端行为。页面中的“合并到原仓库”只会修改任务所选的 `local_repos/<仓库名>`，不会修改最初复制来源的项目目录。
